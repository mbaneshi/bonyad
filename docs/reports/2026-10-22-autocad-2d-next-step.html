AutoCAD 2D Entity Recommendation

Bonyad · Decision brief · 22 October 2026 · Planning only

Recommendation: add one revisioned polyline entity as the next bounded vertical slice. Do not introduce a generic AutoCAD entity table or a universal CAD schema yet.

Repository context

Bonyad currently has stable entity identities, independent point/line/surface geometry, pure Rust validation and measurement, PostgreSQL persistence, and project-level revisions. The current schema deliberately keeps geometry rules in Rust and storage integrity in PostgreSQL.

Research also distinguishes geometry from engineering meaning, and stable Bonyad identity from identifiers supplied by external formats such as DXF.

Evidence: db/migrations/20261021000001_geometry.sql, db/migrations/20261022000004_revisions.sql, logic/crates/geometry/src/types.rs, docs/research/mappings/point-line-surface.md.

Proposed model

A polyline is ordered 2D drawing geometry. It is not automatically a surface merely because it is closed.

polylines
  entity_id
  closed

polyline_vertices
  entity_id
  position
  x
  y

Use the existing stable entity identity and add a distinct geometry kind, polyline. Preserve the distinction between:

  • Open polyline: an ordered chain of straight segments.
  • Closed polyline: a closed drawing boundary.
  • Surface: an accepted engineering area with its own validity and meaning.

Two-axis type direction

Do not overload one kind field with both geometry and engineering meaning. The long-term direction is:

geometry_kind: point | line | polyline | surface | circle | arc
discipline_kind: none | cad_annotation | survey_point | wall | parcel | ...

This is a design direction, not a reason to add all future columns now. The polyline slice should add only what the current workflow proves necessary.

Implementation scope

The issue should include:

  • PostgreSQL tables for polylines and ordered vertices.
  • Rust domain type, serialization, validation, and measurement behavior.
  • Application/API operation using the existing revision and atomic acceptance path.
  • UI creation, display, selection, and vertex update.
  • Agent capability using the same application operation as the UI.
  • Revision snapshots and reload behavior.
  • Unit, API, contract, agent, and browser tests.

Acceptance criteria

  1. Create an open polyline through the UI and agent.
  2. Create a closed polyline without automatically creating a surface.
  3. Preserve vertex order and stable identity after reload.
  4. Move one vertex through the revisioned operation.
  5. Reject non-finite or otherwise invalid geometry without partial accepted state.
  6. Reject stale revision updates atomically with a clear conflict response.
  7. Ensure UI and agent invoke equivalent typed application behavior.
  8. Pass all existing checks and new end-to-end coverage at mobile, tablet, and desktop widths.

Explicitly outside scope

  • DXF import/export.
  • Bulge arcs and curve flattening.
  • AutoCAD layers, blocks, inserts, layouts, text, dimensions, and styles.
  • Generic JSON entities or an inheritance hierarchy.
  • Automatic conversion of closed polylines into surfaces.

Required delivery workflow

  1. Open one issue for the bounded polyline slice.
  2. Create one worktree and branch from synchronized dev.
  3. Implement and test only that issue.
  4. Open one pull request into dev.
  5. Wait for CI and E2E checks to pass.
  6. Merge the PR into dev; do not develop directly on dev.

Open decision before implementation

Should the first polyline support DXF bulge arcs? Recommendation: no. Begin with straight segments, record curve support as a later issue, and never silently flatten curved source geometry during import.
