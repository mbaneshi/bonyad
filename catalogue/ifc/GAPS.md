# IFC 4.3 catalogue: gaps

Generated by `tools/harvest/ifc` (do not edit by hand). Everything below is a known limit of this harvest, not a guess.

## Not stored on purpose
- **Inverse attributes** (INVERSE clauses) and **derived attributes** (DERIVE clauses) are not catalogue fields: they are computed from other data, and the catalogue holds authoritative data only. Each type lists the names it skipped in its `notes`. Derived redeclarations of inherited attributes are noted too.
- **WHERE rules, UNIQUE rules, global RULEs and FUNCTIONs** (48 functions, 2 rules in the schema) are validation logic, not data shape. Only a few narrow checks are mapped (`positive`, `non_negative`, `unit_interval`), and each is verified against the source text at harvest time. Everything else is dropped.
- **Defined TYPEs** (440) are not catalogue types: they are resolved into the field type. Measure types without a catalogue measure (mass, force, time...) become `float`; their unit is the project's IfcUnitAssignment, so the unit is a property of the project, not of the column.

## Lossy mappings (documented in each field's `source_ref`)
- **SELECTs made only of value types** (50 attributes, e.g. IfcValue, IfcMeasureValue) are stored as `text`; which member type was chosen is not kept. List attributes of such a select become `array of text`.
- **SELECTs mixing entities and value types** (11 attributes) are stored as `ref` to `any`; the value members cannot be held in that column. Their types carry `needs_review: true`: `IfcAppliedValue.AppliedValue -> IfcAppliedValueSelect`, `IfcFillAreaStyleHatching.StartOfNextHatchLine -> IfcHatchLineDistanceSelect`, `IfcMetric.DataValue -> IfcMetricValueSelect`, `IfcRelDefinesByProperties.RelatingPropertyDefinition -> IfcPropertySetDefinitionSelect`, `IfcSurfaceStyleRendering.DiffuseColour -> IfcColourOrFactor`, `IfcSurfaceStyleRendering.TransmissionColour -> IfcColourOrFactor`, `IfcSurfaceStyleRendering.DiffuseTransmissionColour -> IfcColourOrFactor`, `IfcSurfaceStyleRendering.ReflectionColour -> IfcColourOrFactor`, `IfcSurfaceStyleRendering.SpecularColour -> IfcColourOrFactor`, `IfcTrimmedCurve.Trim1 -> IfcTrimmingSelect`, `IfcTrimmedCurve.Trim2 -> IfcTrimmingSelect`.
- **SELECTs of entities** become `ref` to the nearest common ancestor type, or `any` when there is none.
- **LOGICAL** attributes become nullable `bool` (UNKNOWN stored as NULL).
- **Lists of lists of entities** (grid): `IfcBSplineSurface.ControlPointsList`. Child table with one `item` ref; the inner row grouping needs a second ordinal. `needs_review: true`.
- Aggregates (LIST, SET, ARRAY, BAG) of scalars are `array` fields; aggregates of entities, enums or lists of lists are child tables. Bounds (`[1:?]`) are kept in the child's notes only. Child types owned by an abstract type are rows of its concrete subtypes.
- IFC geometry (IfcCartesianPoint, IfcDirection) is kept as the source defines it (entities with an `array of length`), not collapsed into point3/vector3. Collapsing is a generator decision.
- Angles: IFC stores them in the project's plane-angle unit (degrees or radians). The catalogue says radians; the importer converts.
- IfcTimeStamp (seconds since 1970) maps to `timestamp`; the importer converts.
- `kind` is assigned by a rule (see README): entity = IfcProduct and IfcRepresentationItem descendants; symbol = type objects, materials, profiles, presentation styles, property set definitions and templates; object = everything else; abstract = ABSTRACT SUPERTYPE. It is a judgement, not something the schema states.

## Source limits
- The newest **EXPRESS** file that is readable in the public repository is IFC4X3_RC4 (issue date 2021-07-22). The final IFC 4.3 releases (ADD1, ADD2, 4.3.2.0) are published as EXPRESS on standards.buildingsmart.org, which returned a bot challenge (HTTP 403) to the one URL tried from this machine; no other mirror was tried, so they were not read. The development repository keeps the later model only as UML/XMI, which was not parsed. ## Not covered by design
- Property set templates and quantity set **content** (the standard Pset_* / Qto_* definitions) are data in `docs/properties`, not part of the EXPRESS schema. Only the generic structures (IfcPropertySet, IfcProperty*, IfcElementQuantity, IfcPhysicalQuantity*) are covered.
- IFC4.3 **MVD / concept templates**, the EXPRESS-G diagrams, and IFC2x3 / IFC4 / IFC4.1 / IFC4.2 schemas. Version differences are not modelled.
- The **bSDD** dictionary.
- File exchange (STEP/IFC parsing, ifcXML, IFC5/IFCX) is a later phase.
